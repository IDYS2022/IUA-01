# IUA — IDYS Advanced Reasoning UI/UX Agent

UIUX 분석만 하는 **디자인 지식 비서**. 복잡한 화면일수록 원리로 핵심을 짚는다.
이디스(IDYS)는 IUA를 만들고 지식을 승인하는 디자이너다.

- **정답지가 아니다.** UIUX에 절대적인 정답은 없다. IUA는 정답에 가까운 방향을 전문 지식에 기대어 내놓는다.
- **꺼낼 곳을 찾아 주는 지식이다.** UIUX에서 상식으로 불리는 지식(닐슨 · 노먼 · 슈나이더만 · 게슈탈트 같은 체계, 사람에 대한 사실, 원리, 화면 상황, 실제 결정 사례)을 기록하고, 필요할 때 그 자리에 맞는 논리를 꺼내 추론에 쓴다.
- **근거를 밝힌다.** 판단마다 무엇에 기댔는지(단위 번호 · 체계 키 · 출처 · 근거 등급)를 보인다. 전문 용어는 원어와 출처가 있다 (`knowledge/_glossary.md`).
- **틀리는 것을 두려워하지 않는다.** 틀린 판단은 사람의 결정과 견주어 사례가 되고, 지식이 자란다. 건강하고 발전적인 생각에 적극적으로 쓰이는 것이 목적이다.

맥락 카드를 받아, 그리기 전에는 설계 요구서를, 그린 뒤에는 진단서를, 질문에는 근거를 밝힌 답을 낸다. 부품과 값은 정하지 않는다. 그것은 그리는 쪽과 그 디자인 시스템의 일이다.

지식 문서는 두 가지로 쓰인다. 사람이 배우는 교보재, 그리고 에이전트가 맥락에 UIUX를 적용할 때 빠르게 꺼내는 참고 자료. 같은 파일이다.

## 쓰는 법

쓰이는 방식은 둘이다.

| 방식 | 어떻게 |
|---|---|
| **직접 묻기** | 사람이 이 저장소에서 연 대화(IUA 섹션)에서 묻는다. 대화는 `AGENTS.md`대로 IUA로서 답한다 |
| **작업 중 부르기** | 디자인 에이전트(예: IDA)가 작업하다 필요한 분석만 에이전트 `iua:iua`로 부른다 |

### Claude Code 플러그인으로

```
/plugin marketplace add IDYS2022/IUA-01
/plugin install iua@iua
```

비공개 저장소라 이 저장소를 읽을 수 있는 git 인증이 필요하다. 설치하면 두 가지가 생긴다.

| 이름 | 무엇 | 누가 쓰나 |
|---|---|---|
| 에이전트 `iua:iua` | 맥락 카드를 받아 요구서 · 진단서를 낸다 | 맥락 파악 에이전트 · 메인 대화가 Agent 도구로 부른다 |
| 스킬 `/iua:consult` | IUA에게 맡기는 순서 (카드 채우기 → 부르기 → 넘기기) | 부르는 쪽 |

설치 없이 시험: `claude --plugin-dir <이 저장소 경로>`. 구조 검사: `claude plugin validate .`

### 플러그인 없이

이 저장소를 읽을 수 있는 AI는 `AGENTS.md` 순서대로 IUA 역할을 직접 한다. 도구는 파이썬 표준 라이브러리만 쓴다.

### 주고받는 양식

부르는 쪽은 `protocol/README.md` 한 장만 읽는다. IUA의 지식은 읽지 않는다.

## 읽는 순서

| 누가 | 순서 |
|---|---|
| IUA (에이전트) | `IUA_CORE.md` → 렌즈 1장 → 체계 훑기(`tools/iua.py frame 닐슨` …) → 신호 · 낱말로 더 찾기 → 고른 단위의 카드 |
| 부르는 에이전트 | `protocol/README.md`의 양식 한 장만 |
| 사람 (배우기) | 이 문서 → 서가 순서대로 `knowledge/FA/` → `PR/` → … 또는 궁금한 렌즈(`LN/`)에서 시작해 `뿌리`를 따라 내려간다. 지도 둘: 왜 사슬 `knowledge/_index/map.md` · 체계 색인 `knowledge/_index/frameworks.md` |

## 지식 여섯 종류

| 기호 | 종류 | 답하는 질문 | 뿌리로 가리킬 수 있는 것 |
|---|---|---|---|
| FA | 사실 | 사람은 어떻게 보고, 기억하고, 고르고, 움직이나 | 없음 (출처가 뿌리) |
| PR | 원리 | 그래서 디자인은 무엇을 지켜야 하나 | FA |
| TN | 긴장 | 원리 둘이 맞서면 어느 쪽이 이기나, 어떤 조건에서 | PR 2개 |
| ST | 상황 | 이 상황에서는 무엇을 하고, 무엇을 하지 않나 | PR · TN |
| CS | 사례 | 실제 화면에서 무엇이 핵심이었고, 어떻게 풀렸나 | ST · PR · TN |
| LN | 렌즈 | 이런 문제는 어디부터, 어떤 순서로 보나 | PR · TN · ST |

사실 → 원리 → 상황 → 사례가 '왜 사슬'이다. 모든 상황은 원리에, 모든 원리는 사실에 이어진다. 끊긴 줄은 `iua.py check`가 알린다. 긴장은 원리 사이에, 렌즈는 사슬로 들어가는 문에 있다.

## 한 파일, 세 깊이

| 깊이 | 무엇 | 누가 여기서 멈추나 |
|---|---|---|
| 머리표 + 한 줄 | 번호 · 신호 · 뿌리 · 근거, 주장을 줄인 한 문장. 색인에는 이 칸만 실린다 | 찾는 중인 에이전트 |
| 카드 | 종류별 칸 4~5개. 12줄 이하 (임시) | 분석 중인 에이전트 |
| 강의 | 왜 그런가 · 흔한 오해 · 복잡한 화면에서 · 사례 · 출처. 길이 제한 없음 | 사람, 그리고 카드로 답이 안 날 때 |

양식과 칸마다 쓰는 법은 `knowledge/_format.md`.

## 근거 등급과 상태

| 근거 | 뜻 | IUA가 말하는 방식 |
|---|---|---|
| A | 실험과 측정으로 여러 번 확인됨 | 사실로 말한다 |
| B | 표준 · 가이드라인 · 전문가 합의 | 권고로 말한다 |
| C | 실무 관례 | 관례로 말하고 맥락을 먼저 본다 |
| D | 우리의 추론 | 가설로 말하고 '결정할 것'에 올린다 |

근거는 증거의 **종류**다 (실험 · 측정이 뿌리면 A, 표준 · 지침 · 전문가 합의면 B). 어디까지 확인했는지는 머리표의 `확인` 칸(원문 · 2차 · 미확인)에 따로 적는다. A · B는 원문이나 2차로 확인한 출처가 있어야 받는다. 확인이 2차면 IUA는 한 단계 낮춰 말한다 (A를 권고로, B를 관례로). 우리가 정리한 것(긴장의 '이기는 조건', 렌즈의 순서)은 D다.

| 상태 | 뜻 | 올라가는 조건 |
|---|---|---|
| 초안 | 써 두었으나 사람이 보지 않음 | – |
| 검토됨 | 이디스가 읽고 승인함 | 사람의 승인 |
| 확립 | 실전에서 맞은 것이 확인됨 | 사례 3건에서 사람의 결정과 맞음 |
| 폐기 | 틀렸거나 다른 단위로 합쳐짐 | 지우지 않고 머리표에 `대신: <번호>` |

## 서가 열두 곳 (`영역` 칸의 값)

사람 · 일과 맥락 · 정보 구조 · 시각 구조 · 상호작용 · 흐름 · 내용과 말 · 시간과 움직임 · 접근성과 포용 · 기기와 매체 · 신뢰와 윤리 · 복잡한 시스템

## 운영 규칙 — 지식이 들어오는 길과 올리는 법

| 길 | 어떻게 | 주로 느는 종류 | 처음 상태 |
|---|---|---|---|
| 집필 | 서가의 빈 곳을 계획해서 쓴다. IUA가 초안, 이디스가 읽는다 | FA · PR · TN · LN | 초안 |
| 되먹임 | 분석 → 사람의 결정 → 사례 1장. 사람이 요구를 고쳤으면 그 차이가 가장 값진 기록 | CS · ST | 사례는 바로 기록, 새 상황은 후보 |
| 문헌 연구 | 책 · 논문 · 가이드라인을 확인한 출처와 함께 우리 말로 옮긴다 | FA · PR | 초안 |

- 쓰기 전에 찾는다 (`iua.py find`). 같은 주장이 있으면 그 장을 고친다.
- 같은 추론(근거 D)이 사례 3건에서 반복되고 사람의 결정과 맞으면 상황 단위로 올린다. 세는 일은 `iua.py check`가, 올리는 결정은 사람이.
- 사람과의 고찰 대화에서 나온 판단 양상과 빈칸은 대화가 끝날 때 IUA가 뽑아 보이고, 사람이 고른 줄만 `knowledge/_candidates.md`에 둔다. 정식 지식이 아니라 선례다 (추론 · D). `find`가 맞는 3줄까지만 보이고, 전체는 40줄을 넘지 않는다. 사례 3건이 뒷받침하면 정식 단위로 올린다.
- 새 지식이 있는 지식과 맞서면 한쪽을 지우지 않는다. 조건을 따져 긴장 단위를 쓰거나 '약해지는 때'에 더한다.
- 취향은 부르는 쪽의 결정 기록(사람이 내린 디자인 결정)으로, 원리는 IUA로. 가르는 질문: 다른 디자이너의 프로덕트에서도 참인가.
- 회사 · 프로덕트 이름을 넣지 않는다 (IUA의 지식은 어느 서비스에도 쓰는 범용이다). 사례의 서비스는 종류로 부른다 (AI 생성 도구 · 협업 도구).
- IUA는 혼자 선다. 특정 에이전트 · 저장소의 이름 · 파일 경로 · 규칙 번호 · 디자인 시스템 고유의 이름을 지식에 넣지 않는다. 그 에이전트에 맞추는 일은 그 에이전트 쪽에서 한다.
- 번호는 한 번 주면 다시 쓰지 않는다. 폐기도 번호를 남긴다.
- 체계(닐슨 · 노먼 · 슈나이더만 · 게슈탈트 …)의 항목과 단위의 연결은 `knowledge/_frameworks.md` 한 곳에만, 전문 용어는 `knowledge/_glossary.md`에 원어 · 출처와 함께 적는다.
- 출처는 확인한 것만 적는다. 확인 못 했으면 `출처 미확인`. 출처 절의 발행처 이름은 된다.
- 저장 전 `iua.py check` → 문제 0. 단위를 더하거나 고쳤으면 `iua.py index`. `knowledge/_index/`는 손으로 고치지 않는다.
- 커밋 메시지에 왜 바꿨는지 쓴다. 플러그인 구조(`.claude-plugin/` · `agents/` · `skills/`)를 바꿨으면 `claude plugin validate .`도 돌린다.

## 도구

```bash
python3 tools/iua.py check              # 양식 · 어휘 · 끊긴 줄 · 한도 · 올릴 후보. 저장 전에
python3 tools/iua.py index              # _index/ 다시 만들기. 단위를 더하거나 고친 뒤
python3 tools/iua.py frame              # 체계와 키 목록 (닐슨-1 … · 노먼-시그니파이어 …)
python3 tools/iua.py frame 닐슨-5       # 그 항목의 근거 단위 (한 줄). 'frame 닐슨'은 10개 전부
python3 tools/iua.py find 초심자 입력   # 신호로 찾기 (한 줄). --type PR
python3 tools/iua.py find --text 시그니파이어   # 낱말로 찾기 (단위 본문 · 체계 목록 · 용어집)
python3 tools/iua.py card PR-001        # 카드만
```

## 어디서 왔나

IUA는 처음에 'UPA(UIUX Professor Agent)'라는 이름으로 디자인 에이전트 안에 들어가 시작했다 (2026-11-06 기획). 여러 에이전트가 서로 부르며 일하게 하려고 2026-11-11 독립 에이전트로 떼어 내고 이름을 IUA로 바꿨다.

- 지식의 출처 절에 나오는 '디자인 결정 기록 D##'은 이디스가 실제로 내린 디자인 결정이고, '디자인 판단 절차(이디스)'는 이디스의 판단 절차에서 옮긴 관례다.
- 맥락 카드의 칸 번호(M1~M7)와 화면 유형 8개도 디자인 판단 절차(이디스)에서 가져와 IUA의 것으로 두었다.
