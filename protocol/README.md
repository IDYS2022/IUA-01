# 주고받는 양식 — IUA를 부르는 에이전트는 이 한 장만 읽는다

IUA는 어느 맥락 에이전트가 불러도 같은 양식으로 받고 같은 양식으로 낸다. 부르는 쪽은 IUA의 지식을 읽지 않는다.
(초안. 3단계에서 실제 요청으로 다듬는다)

## 부르는 법

| 어디서 | 어떻게 |
|---|---|
| Claude Code (플러그인 설치) | Agent 도구로 `subagent_type: "iua:iua"`를 부르고, prompt에 아래 맥락 카드를 넣는다. 부르는 순서와 돌아온 것을 쓰는 법은 스킬 `/iua:consult` |
| 플러그인 없이 (다른 AI · 다른 도구) | 이 저장소를 읽을 수 있으면 `AGENTS.md` 순서대로 IUA 역할을 직접 한다 |

## 받는 것 — 맥락 카드

한 칸 한 문장. 모르면 `모름`, 짐작이면 `가정:`을 붙인다. 필수 칸이 비면 IUA는 되물을 질문을 돌려준다.

| 칸 | 묻는 것 | 언제 |
|---|---|---|
| 일 | 사전 분석 · 사후 진단 · 강의 중 하나 | 늘 |
| M1 서비스 | 누가 · 어디서(기기) · 얼마나 자주 · 왜 쓰나 | 필수 |
| M2 화면의 일 | 이 화면에서 끝낼 일 하나와 끝났다는 조건 ("___ 하면 끝") | 필수 |
| 유형 | 홈 · 목록 · 상세 · 입력·편집 · 작업 공간 · 대시보드 · 설정 · 단계 진행 중 주 유형 1개 (+ 구역) | 필수. 모르면 IUA가 M2로 정하고 `가정:`을 붙인다 |
| M3 흐름 | 끝내는 순서. 자주 하는 일 / 되돌릴 수 없는 일 | 있으면 |
| M4 정보 관계 | 무엇이 무엇을 지배하나 ("A > B > C"). 지금 위치 | 있으면 |
| M5 요소 역할 | 요소마다 역할 하나 | 사후 진단 |
| M6 묶음 이름 | 묶음 이름과 안의 항목 | 있으면 |
| M7 모순 | 기획서와 어긋나는 곳 | 기획서가 있을 때 |
| 화면 | 스크린샷 경로 또는 화면 설명 | 사후 진단 필수 |
| 요구서 | 앞서 받은 설계 요구서 | 사후 진단에 있으면 |
| 증상 | 사람이 한 말 ("복잡해 보인다" 등) | 사후 진단에 있으면 |
| 난이도 | 보통 · 어려움 | 없으면 IUA가 정한다 |

```
맥락 카드
일: 사전 분석
M1 서비스: IT가 낯선 현장 담당자가 매일 휴대폰 · PC로 작업자를 배치하고 메신저로 명단을 보낸다
M2 화면의 일: 그날 모든 작업에 빠짐없이 · 겹치지 않게 사람을 넣고 명단을 보내면 끝
유형: 작업 공간 (구역: 일정 요약)
M3 흐름: 날짜 → 남은 사람 → 배치 → 확인 → 복사. 비우기 · 삭제는 드묾
M4 정보 관계: 하루|한 주 > 날짜 > 그날 데이터. 지금 위치 = 고른 날
난이도: 어려움
```

- 칸 번호(M1~M7)와 유형 8개는 디자인 판단 절차(이디스)에서 가져와 이제 IUA의 것으로 둔다. 부르는 에이전트는 자기가 아는 맥락을 이 칸에 옮겨 넘긴다. 칸 이름이 같은 카드를 이미 쓰는 에이전트는 그대로 넘기면 된다.
- 신호는 부르는 쪽이 고르지 않는다. IUA가 카드의 말을 `knowledge/_vocab.md`의 신호로 바꾼다.

## 내는 것 1 — 설계 요구서 (사전 분석. IUA → 그리는 에이전트)

```
설계 요구서 · 화면: <이름> · 렌즈: LN-… · 난이도: 보통 / 어려움

핵심
  <한 문장. 이 화면에서 반드시 이뤄져야 하는 것 하나>

지배 원리 (3개 이하)
  PR-… <제목>        <이 맥락에서 뜻하는 것 한 줄>

요구 (무엇이 이뤄져야 하나. 7개 이하. 부품과 값은 적지 않는다. 근거 번호는 원리의 '요구로 바꾸면' 또는 상황 단위)
  R1 …                PR-… · 근거 B
  R2 …                ST-… · 근거 D · 추론        ← 지식에 없어 추론한 요구는 이렇게 표시
  R3 …                ST-… · 근거 B · 초안        ← 초안 상태의 지식으로 낸 요구는 '초안'을 함께

버린 것 (비우지 않는다. 없으면 "없음"과 이유)
  <진 요구> — 이긴 쪽: <원리> · 이유        TN-…

확인 질문 (그린 뒤 예 / 아니오. 요구에서 나온 것만)
  Q1 …
  Q2 …

모름 · 가정
  가정: …   /   모름: … → 맥락에 되물음
```

- 그리는 에이전트는 요구마다 "어떻게 풀었나"를 보고에 적는다. 디자인 시스템으로 풀 수 없는 요구는 몰래 바꾸지 않고 '결정할 것'에 올린다.
- 난이도 '보통'이면 핵심 · 지배 원리 1~2 (렌즈가 가리키는 것, 한 줄만 읽고) · 요구 3줄 이하로 줄인 짧은 요구서.

## 내는 것 2 — 진단서 (사후 진단. IUA → 사람, 그리는 에이전트가 함께 본다)

```
진단서 · 화면: <이름> · 본 것: 스크린샷 1장 / 흐름 n단계 · 요구서: 있음 / 없음

확인 질문
  Q1 예 · Q2 아니오 · Q3 모름

발견 (무거운 순서로, 5개 이하)
  1 [막힘]    어디: …  무슨 일: …  왜: PR-…  이뤄져야 할 것: …
  2 [헷갈림]  어디: …  무슨 일: …  왜: PR-…  이뤄져야 할 것: …
  3 [거슬림]  어디: …  무슨 일: …  왜: ST-…  이뤄져야 할 것: …

잘된 것 (고칠 때 지킬 것)
  …

모름 (사람이나 맥락에 물을 것)
  …
```

| 무게 | 뜻 | 그다음 |
|---|---|---|
| 막힘 | 화면의 일을 끝낼 수 없다 | 고치기 전에는 통과가 아니다 |
| 헷갈림 | 끝낼 수는 있지만 틀리거나 망설인다 | 고치거나, 두는 이유를 '결정할 것'에 |
| 거슬림 | 끝내는 데 지장은 없다 | 목록으로 남긴다 |

- 진단서도 방향까지만 쓴다. 어떤 부품으로 고칠지는 그리는 에이전트가 정한다.
- 숫자로 잴 수 있는 것(여백 · 대비 · 크기 · 가로 넘침)은 그리는 쪽의 검사 도구가 잰다. 진단서에 넣지 않는다.

## 되묻기 — 필수 칸이 비었을 때

틀렸을 때 다시 하는 비용이 크면 요구서 대신 이것만 돌려준다. 비용이 작으면 `가정:`을 붙이고 요구서를 낸다.

```
되묻기 · 답에 따라 지배 원리가 바뀌는 것만 (3개 이하, 보기 2~3개)
  Q1 … (보기: … / … ) — 바뀌는 것: PR-… ↔ PR-…
```
